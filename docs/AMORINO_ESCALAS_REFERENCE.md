## 1. What the app is

**Amorino Escalas** is an internal web app for managing weekly work-shift schedules ("escalas") across **five Amorino gelato stores** in Porto and Gaia, Portugal. It is used by roughly **30 staff** plus one supervisor/owner.

The five stores ("lojas"):

| id | name | short |
|----|------|-------|
| `carmelitas` | Carmelitas | CRM |
| `clerigos` | Clerigos | CLR |
| `norte` | Norte Shopping | NST |
| `gaia` | Gaia | GAI |
| `mbs` | Mercado Bom Sucesso | MBS |

The real-world problem it solves: every week, someone has to decide who works which shift in which store, balancing each person's contracted hours, their stated availability and preferences, store opening/closing coverage rules, and Portuguese public-holiday double-pay days. Staff then need to see their own shifts, swap shifts with each other, and submit availability for upcoming weeks. Before this app, that was spreadsheets and PDFs from the franchise tool ("CAEM").

**Two primary user experiences:**

- **Employee** ("funcionário"): sees their own schedule, submits availability, swaps shifts, subscribes to a personal calendar feed.
- **Supervisor/owner** ("ADMIN"): builds the schedule for all five stores using a day-first planner with an automatic suggestion engine, manages staff, approves swaps, exports PDFs.

It is a **single-process Flask app**, server-rendered Jinja templates plus vanilla JavaScript. No SPA, no build step, no external services. SQLite database.

## 2. Tech stack and architecture

- **Backend:** Python 3.12+ · Flask 3 · SQLAlchemy 2 (declarative ORM)
- **Database:** SQLite. Path from env var `AMORINO_DB_PATH` (default `amorino.db` in the working dir).
- **Frontend:** Jinja2 server-rendered templates + vanilla JS. No React, no bundler. Each page carries its own `<style>` and `<script>`; `base.html` provides the shell, nav, and a global `toast()` helper.
- **Auth:** Flask sessions, cookies `HttpOnly` + `SameSite=Lax` + `Secure` in production. Session lifetime 12h, enforced by a `before_request` hook.
- **PINs:** PBKDF2-SHA256 via `werkzeug.security`. Legacy plaintext PINs are auto-upgraded to a hash on the next successful login.
- **CSRF:** one token per session, validated on every mutating request (`POST`/`PUT`/`PATCH`/`DELETE`) except an allow-list of exempt endpoints (login, the cookie-less calendar feeds).
- **iCal:** RFC 5545 generated by hand (no library). QR codes via the `qrcode` package in pure-SVG mode (no PIL).
- **PDF export:** ReportLab (`gerar_pdf.py`).
- **Historical PDF parsing:** `pdfplumber`, used only by the offline `import_history.py` CLI — **not** at app runtime.

**Dependencies** (`requirements.txt`):

```
flask>=3.0
flask-sqlalchemy>=3.1
holidays>=0.40
qrcode>=7.4
reportlab>=4.0
```

> Note: `holidays`, `qrcode`, and `reportlab` are **runtime** dependencies — the app will not start without `holidays`, and the calendar/PDF features need the other two. `pdfplumber` is only needed if you run the importer and is intentionally not pinned in `requirements.txt`.

**Architectural decisions worth knowing:**

- **Constants and models are extracted; routes are not.** A May 2026 refactor split the original monolith into `config.py` (constants), `extensions.py` (the `db` singleton), `models.py`, `seed_data.py`, and a `helpers/` package. The ~55 routes deliberately stay in `app.py` — splitting them into blueprints is net-negative for a one-person team. Noted as a future option, not a to-do.
- **No Alembic migrations yet.** Schema changes are done with hand-written `ALTER TABLE` in the DB-init block of `app.py`. Fragile but adequate at this scale. **If you add a model column, you must also add the matching `ALTER TABLE`.**
- **Everything is server-rendered.** The `/api/*` endpoints exist only for interactions that need an update without a full reload (drag-and-drop assignment, the empties panel, swaps). Everything else is Jinja returning full HTML.

## 4. Roles and permissions

Three effective levels, driven by the session (`user_sigla`) and an `is_supervisor` flag.

### Funcionário (regular employee)
- Sees **their own** schedule at `/minha-escala`.
- Submits/edits **their own** availability at `/disponibilidade`.
- Sees the full schedule **read-only** at `/escala`.
- Sees the team roster at `/equipa` (reduced info — no PINs).
- Creates, cancels, and responds to swap requests at `/trocas`; participates in the open marketplace ("central").
- Generates a personal iCal subscription link to put their shifts on their phone.

### Higher-rank employee (`shift_supervisor` / `store_manager`)
- Everything a regular employee does. Rank affects **coverage rules** (who may open/close a store alone), not app permissions. By default, swap approval is still supervisor-only.

### Supervisor / owner (`ADMIN`)
- The editable planner at `/supervisor/escala`: add/remove/move shifts, one-click assign from suggestions, manage headcount targets.
- The dashboard at `/supervisor` (employees are redirected here from `/`).
- Approves/denies swap requests and chooses donation recipients; only the author cancels a request.
- Conflict validator `/supervisor/conflitos`; aggregated availability `/supervisor/disponibilidades`.
- PDF exports.

The supervisor is a special sigla (`ADMIN` by default, in `config.ADMIN_SIGLA`) with a PIN from `AMORINO_SUPERVISOR_PIN`. Its login rate-limit is stricter (5 vs 8 attempts / 5 min).

**Key permission boundary — the swap "central":** employees publish and apply; the admin cannot apply or cancel on their behalf. For genuine exchanges, the author chooses a proposal before admin review. For donations, the first application enters "A aprovar" immediately, without a nominated recipient, and only the admin can choose and approve one candidate. Donation `/escolher` requests return 403; the admin's selection goes through `/decidir`.

## 5. Domain glossary

Read this before the data model — the schema names assume these concepts.

- **Loja** — a store. Five of them (see §1). Identified by a short id string.
- **Turno** — a single shift: one person, one store, one time-band, on one day of one week.
- **Horário** — a time-band string like `08:00-16:30`, `13:00-22:00 (+0,5)` (the `(+0,5)` is a paid half-hour marker), or `16:00-00:30` / `15:00-00:30 (+1)` (crosses midnight; `(+1)` = ends next day). Some "horários" are non-time placeholders like `Provas Praticas` (practical exams) — the schedule grid renders them as rows but they aren't real time bands.
- **Slot** — a coarse part-of-day bucket derived from a horário's start time: `manha` / `tarde` / `noite` / `fecho`. Used by availability and scoring. Computed by `horario_to_slot()`.
- **Dia** — a day *label* relative to its week, e.g. `Seg 11`, `Dom 17`. **The label alone is not a date.** The real date lives in `SemanaConfig.dias_json`.
- **Semana** — a week, identified by a `codigo` like `11-17mai`. `SemanaConfig` holds its label, its seven days (with dates and holiday info), and whether it is the "active" week.
- **Disponibilidade** — what an employee submits for a week: preferred stores, preferred slots, a type (preference vs available vs extra), and a note. Per day.
- **Troca** — a shift swap. Two flavours: **direto** (A asks B directly) and **aberto** (published to the central marketplace for anyone to apply). A **doação** is a one-way give-away (no shift back).
- **Candidatura** — a colleague's application to an open ("aberto") troca.
- **Rank** — employee hierarchy: `trainee` < `staff` < `shift_supervisor` < `store_manager`. Governs who can open/close a store alone.
- **Headcount target** — for a `(loja, weekday)`, how many *people* are expected. Drives the "faltam N" badges and the suggestion priority. **Counts people, not shifts** (see §11).
- **Descarga** — an unloading/stock task that can be made available on specific days of a week.
- **Feriado** — a public holiday; on these days pay is doubled ("paga em dobro"). Surfaced in the UI and the calendar feed.
- **CAEM** — the franchise's scheduling tool, whose PDF exports `import_history.py` parses for historical data.

## 6. Data model

All models live in `models.py`. The `db` instance is imported from `extensions.py`. **This is the exact current schema.**

### `Turno` — table `turnos`
```
id           INT PK
loja         VARCHAR(30)   NOT NULL   # 'carmelitas' | 'clerigos' | 'norte' | 'gaia' | 'mbs'
horario      VARCHAR(60)   NOT NULL   # '08:00-16:30', '16:00-00:30', 'Provas Praticas', ...
dia          VARCHAR(20)   NOT NULL   # label relative to the week, e.g. 'Seg 11'
funcionario  VARCHAR(10)   NOT NULL   # FK by convention → funcionarios.sigla
nota         VARCHAR(100)  default ''
semana       VARCHAR(20)   default '11-17mai'   # → SemanaConfig.codigo
updated_at   DATETIME      default now(utc)     # set on insert; "schedule freshness"
```
**No unique constraint** on `(funcionario, semana, dia, horario, loja)` — deliberate, so the same person can appear in two places (a "Troca de Loja" case). The importer enforces idempotency in Python instead. A `Turno` carries its own `semana`, which is what makes **cross-week swaps** work.

### `Funcionario` — table `funcionarios`
```
sigla           VARCHAR(10) PK         # 2-4 uppercase letters, e.g. 'BG', 'HGA'
nome            VARCHAR(80) NOT NULL
horas_contrato  INT default 0          # contracted hours/week; 0 = pure on-call
pin             VARCHAR(200) default ''# PBKDF2 hash (legacy plaintext auto-upgraded)
tipo_contrato   VARCHAR(10) default 'contrato'  # 'contrato' | 'turnos'
rank            VARCHAR(20) default 'staff'     # trainee|staff|shift_supervisor|store_manager
ical_token      VARCHAR(64) default ''          # bearer secret for the calendar feed
```
Properties: `is_turnos`, `is_contrato`, `rank_level`, `can_open_alone` (rank ≥ staff), `can_close_alone` (rank ≥ shift_supervisor). `tipo_contrato` is somewhat redundant with `horas_contrato == 0` but kept for clarity. There is no `is_supervisor` *column* — supervisor status is the `ADMIN` sigla + session flag.

### `Disponibilidade` — table `disponibilidades`
```
id            INT PK
semana        VARCHAR(20) NOT NULL
funcionario   VARCHAR(10) NOT NULL
dia           VARCHAR(20) NOT NULL
tipo          VARCHAR(20) NOT NULL    # 'preferencia' | 'disponivel' | 'extra'
texto         VARCHAR(200) default ''
lojas_pref    VARCHAR(120) default '' # CSV of loja ids; empty = any
slots_pref    VARCHAR(120) default '' # CSV of slot codes; empty = any
submetido_em  DATETIME default now(utc)
revisto       BOOLEAN default False   # supervisor marked it reviewed
```
Empty `lojas_pref`/`slots_pref` means "anywhere/anytime". `tipo='preferencia'` with both empty = "wants to work, wherever".

### `SemanaConfig` — table `semanas`
```
id            INT PK
codigo        VARCHAR(20) UNIQUE NOT NULL   # '11-17mai'
label         VARCHAR(60) NOT NULL          # '11 a 17 de Maio'
dias_json     VARCHAR(500) NOT NULL         # JSON list of {label,date,feriado,feriado_nome}
ativa         BOOLEAN default True          # the "current" week for employees
descarga_dias VARCHAR(120) default ''       # CSV of day labels where descarga is offered
criada_em     DATETIME default now(utc)
```
`dias_json` is the **canonical source of dates**. A `Turno.dia` is only the label; to get a real date you look up `dias_json[idx].date`. Each day entry: `{label, date, feriado (bool), feriado_nome (str)}`.

### `HorarioBloco` — table `horario_blocos`
Supervisor-added custom time-bands for a store, persisted. `loja`, `horario`, `ordem`. Unique `(loja, horario)`.

### `HorarioSupressed` — table `horario_supressed`
Base horários (from `HORARIOS_BASE`) the supervisor has chosen to hide. `loja`, `horario`. (Before this existed, hiding was in-memory and reverted on restart.)

The **effective horários** for a store = `HORARIOS_BASE[loja]` minus `HorarioSupressed` plus `HorarioBloco`, in display order. This is computed in `build_grid()` and (batched) in `api_empties`.

### `LojaHeadcountTarget` — table `loja_headcount_targets`
```
id       INT PK
loja     VARCHAR(40) NOT NULL
dia_idx  INT NOT NULL          # Python weekday(): 0=Mon .. 6=Sun
target   INT NOT NULL default 0
UNIQUE(loja, dia_idx)
```
How many **people** each store needs per weekday. Drives the "faltam N" badges, suggestion priority, and the stale-target banner. Seeded from observed peaks; editable via the "Alvos" modal or `import_history.py --reset-targets`.

### `TrocaPedido` — table `trocas`
```
id                   INT PK
criado_em            DATETIME (indexed)
atualizado_em        DATETIME (onupdate)
de_sigla             VARCHAR(10) NOT NULL (indexed)
para_sigla           VARCHAR(10) NOT NULL default '' (indexed)  # donations: '' until final admin approval
turno_origem_id      INT NOT NULL
turno_destino_id     INT NULL          # NULL = doação (one-way)
motivo               VARCHAR(300) default ''
estado               VARCHAR(30) NOT NULL default 'pendente_colega' (indexed)
resposta_colega      VARCHAR(300) default ''
resposta_supervisor  VARCHAR(300) default ''
decisao_em           DATETIME NULL
tipo                 VARCHAR(20) NOT NULL default 'direto' (indexed)  # direto|aberto_doacao|aberto_troca
origem_snapshot_json TEXT NOT NULL default ''  # published donation shift identity
```
State machine (see §7).

### `TrocaCandidatura` — table `trocas_candidaturas`
```
id                 INT PK
troca_id           INT NOT NULL (indexed)
sigla              VARCHAR(10) NOT NULL (indexed)
comentario         VARCHAR(300) default ''
turno_oferecido_id INT NULL          # the shift THEY offer (aberto_troca); NULL for doação
criado_em          DATETIME
status             VARCHAR(20) default 'pendente' (indexed)  # pendente|aceite|rejeitada|retirada|vetado|negada|cancelada|expirada
```

### `AuditLog` — table `audit_log`
```
id, ts (indexed), actor, ip, action, target, detail
```
Append-only. General actions use the best-effort `helpers.audit.audit()`. Donation transitions use `helpers.donations.transaction_audit()` in the same transaction as the decision and transfer; an audit storage failure rolls the transaction back. No UI — read it with a SQL client on purpose.

> **History note:** a duplicate `audit()` *function* once lived in `models.py` and referenced `request`/`session`/`log` without importing them (dead code that would `NameError` if called). It was removed. The live `audit()` is in `helpers/audit.py`.

## 7. Core domain mechanics

### Weeks and dates
- A week is a `SemanaConfig` with `codigo`, `label`, and `dias_json` (the seven days with real dates + holiday flags).
- Exactly the day labels in `dias_json` are valid `Turno.dia` values for that week.
- "Which week is current" has two senses, and they can differ:
  - **Active week** (`SemanaConfig.ativa`) — the supervisor's notion / what's being drafted.
  - **Employee's working week** — the week an employee is actually living right now (resolved by `get_semana_for_employee()` — prefers the active week if it contains today; otherwise the oldest week containing today).
- `time_helpers` builds weeks: `week_from_monday`, `next_mondays`, `week_codigo`, `week_label`. Ordering across weeks uses the real start date (`semana_start_date`, via `semanas_chronological`), **not** the `id` — important because imported history can arrive out of insert order.
- The edit and shared read-only schedule use previous/next arrows and a date range including years. Backend navigation uses only authorised existing weeks and their actual dates; employees see published weeks only. The `semana` parameter preserves deep links, filters and browser history. Boundary arrows are disabled; browsing never creates, activates or publishes a week.

### Shifts and time math
- `shift_bounds(horario)` → `(start_min, end_min)`; handles `(+1)` midnight crossover.
- `shifts_overlap(h1, h2)` → bool. Used for conflict detection and "who's with me today".
- `shift_hours(horario)` → float hours, subtracting a 30-min unpaid lunch when the shift is ≥ 8h (`LUNCH_BREAK_THRESHOLD`).
- `horario_to_slot(horario)` → `manha`/`tarde`/`noite`/`fecho` from the start time.

### Availability
Employees submit per-day availability for a week with a `tipo`:
- **preferência** (green) — "if possible, put me here"
- **disponível** (blue) — "I can work any of these"
- **extra / descarga** (grey) — "I can do unloading if needed"

The supervisor sees it aggregated at `/supervisor/disponibilidades` and can mark entries reviewed (`revisto`).

### The swap state machine (`TrocaPedido.estado`)
```
criar → pendente_colega
            │  (B aceita)            (A cancela, anytime before approval)
            │                                   │
            ▼                                    ▼
   pendente_supervisor                       cancelado
       │  (sup aprova) │ (sup nega)
       ▼               ▼
   aprovado          negado
```
For a genuine open exchange (`aberto_troca`), colleagues offer shifts and the author picks a proposal. That candidatura becomes `aceite` (others `rejeitada`), `para_sigla` is set, and the request moves to `pendente_supervisor`. Admin rejection reopens this exchange, vetoes the chosen candidate and restores the other proposals.

For a donation (`aberto_doacao`), publication starts at `aberto`; the first active candidacy changes it to `pendente_supervisor`. Both states stay in the Central and accept more candidates. Withdrawal of every candidate returns it to `aberto`. `para_sigla` remains empty until the admin explicitly chooses and approves a pending `candidatura_id`; the donor never chooses. Approval marks the winner `aceite` and other active candidates `rejeitada`. Whole-donation rejection closes it as `negado`; donor cancellation gives `cancelado`, and shift start in Europe/Lisbon or invalid shift identity gives `expirado`.

Donation validation checks the published and draft shift identity, candidate eligibility and scheduling rules when applying and again when approving. `BEGIN IMMEDIATE` protects selection, transfer, candidate outcomes, publication and audit in one SQLite transaction. Only the transfer is published; unrelated draft changes remain private. The idempotent migration removes legacy nominations, restores interested candidates for admin review and preserves completed history without approving a transfer; see [DONATIONS.md](DONATIONS.md).

**On approval, the actual `Turno` rows change owner:**
- **doação** (`turno_destino_id` NULL): the origin turno is reassigned to `para_sigla`; `de_sigla` is freed.
- **swap** (both set): `para_sigla` receives the origin turno; `de_sigla` receives the destino turno. Each turno keeps its own `semana`, so cross-week swaps just work.

State sets/labels live in `config.py`: `TROCA_STATES_OPEN`, `TROCA_STATES_CLOSED`, `TROCA_STATE_LABELS`, `TROCA_TIPO_LABELS`.

### Coverage rules (rank-based)
`can_open_alone` = rank ≥ `staff` (trainees cannot open). `can_close_alone` = rank ≥ `shift_supervisor`. The conflict validator warns when a store opens/closes without someone qualified, among other checks. **Warnings never block saving** — the supervisor has the final word.

## 8. The suggestion engine

Lives entirely in `helpers/scoring.py`. Constants in `config.py` (`HISTORICAL_LOOKBACK_WEEKS=12`, `HISTORICAL_MIN_WEEKS=2`, `HISTORICAL_MAX_BONUS=250`).

**Concept.** For each candidate for an empty slot, compute a numeric **score** (higher = better fit) from four factors:

1. **Explicit preference** (1000 / 700 / 500) — what the person said in availability. Highest weight.
2. **Availability** (300) — "I can work, no specific preference".
3. **Historical bonus** (up to +250) — if the person worked that `(loja, weekday, slot)` in recent weeks, a recency-weighted bonus (recent weeks weigh more).
4. **Hours balancing** (±200) — contracted people under their weekly hours get a bonus; the overloaded get a penalty.

**Key functions:**
- `_load_prior_weeks(current_semana_codigo)` — one batched query returning: `n_weeks`, `affinity` `{(sigla, loja, weekday_idx, slot): 0..1}`, `pair_affinity` `{(sigla_a, sigla_b, weekday_idx): float}` (who tends to work together), and `loja_day_counts` for auto-targets. 12-week lookback, recency-weighted, weeks ordered by real date.
- `_score_candidate(...)` → `(score, reason_word)`. The `reason_word` is the single Portuguese word shown on the suggestion chip: `prefere`, `prefere parcial`, `quer trabalhar`, `disponível`, `descarga`, `sem resposta`, `histórico`. `histórico` only fires when the historical bonus is strong **and** the base signal is weak — so someone with an explicit preference is never mislabelled "histórico".
- `_score_best_slot_for_loja(..., return_slot=False)` → by default `(score, reason)`; with `return_slot=True` → `(score, reason, slot)`. The 3-tuple form lets the planner recommend a concrete time band for one-click assignment. **The default 2-tuple form is preserved for backward compatibility — do not change the default.**
- `p75_ceiling(values)` — 75th-percentile-then-ceiling, used to propose headcount targets. Deliberately above the median so you staff for the busy Saturday, not the average day.

**Limits (by design):** no explicit holidays/vacations awareness (remove the availability instead), no skills modelling (everyone interchangeable within a rank), no commute/distance, and the historical bonus is capped at +250 so a *current* explicit preference always outweighs an old pattern.

## 11. Business rules and invariants

**These are the rules that must hold. Breaking one is a bug even if tests pass.**

1. **Headcount counts people, not shift-rows.** In `/api/empties`, both the per-loja `filled` and the day-spine `day_totals.filled` must count **unique siglas**, not the number of `Turno` rows. A person working two time-bands in one store on one day is **one** body toward the target. (Counting rows produced the "3/3 ✓" bug when only 2 distinct people were assigned.)

2. **Approving a swap must re-check for conflicts.** `api_trocas/.../decidir` re-validates before reassigning, because the schedule can drift between when a swap is set up and when it's approved. It must refuse (HTTP 409, `conflito: true`) if approval would put either person in two overlapping shifts — consistent with what `api_turno/add` and `api_turno/move` already prevent on direct edits. Denial must **never** be blocked by this check (denial moves no shifts).

3. **Direct add/move never double-books.** `api_turno/add` and `api_turno/move` reject placing a person in a time-band that overlaps another shift they already hold that day.

4. **One-click suggestions never collide.** Each suggestion's recommended `horario` must be a band the person is **not** already on, so the one-click assign can't 409.

5. **Donation selection belongs exclusively to the admin.** Employee candidacies enter the admin queue immediately; donor `/escolher` is forbidden. The admin selects a pending `candidatura_id` through the final `/decidir` action and cannot apply or cancel on behalf of employees. Genuine exchanges retain author selection before admin review.

6. **Cross-week swaps are supported and must stay so.** A `Turno` carries its own `semana`; approval only reassigns ownership. The swap-selection UI (`turnos-do-colega`) returns shifts across current + future weeks (never past), grouped by week. Don't reintroduce a single-week filter as the default.

7. **The single-shift `.ics` endpoint is private.** `/cal/turno/<id>.ics` serves only the logged-in caller's own shift; it must 404 for anyone else's id and 403/redirect when logged out. It must not become enumerable.

8. **Advisory warnings never block.** Availability, contract-hours and rest warnings remain advisory. Identity drift, ineligible candidates, overlaps and the existing cross-store assignment rule block donation approval.

9. **General `audit()` is best-effort; donation audit is transactional.** Donation evidence must commit with the transfer or the entire action rolls back.

10. **Backward-compatible signatures.** `_score_best_slot_for_loja` returns a 2-tuple by default; the 3-tuple is opt-in via `return_slot=True`. The calendar feed with no `?lembrete` must behave exactly as before (no alarm). Adding a param must not change existing behaviour.

11. **Past shifts can't be swapped.** Swap selection excludes weeks that already ended. Unassigned donations expire at their shift's start in Europe/Lisbon, including those awaiting admin review.

12. **If you add a model column, add the matching `ALTER TABLE`** in the DB-init block of `app.py` (no Alembic yet).

## 12. Security model

Detailed in `SECURITY.md`; summary here.

**Environment variables (must set in production):**
- `AMORINO_DB_PATH` — SQLite path (default `amorino.db`).
- `AMORINO_SECRET_KEY` — Flask session key. **Change in production.** Generate: `python -c "import secrets; print(secrets.token_hex(32))"`. The app warns loudly on startup if it's the default.
- `AMORINO_SUPERVISOR_PIN` — supervisor PIN. **Change in production.** Default `'1234'` (also warns).

**Layers:**
- **Auth:** PBKDF2-SHA256 PINs; legacy plaintext auto-upgrades on first successful login. PIN length 4–32.
- **Rate-limiting:** per-IP (8/5 min; 5 for `ADMIN`) plus a per-process global (30/hour across all IPs).
- **CSRF:** one token per session, checked on all mutating endpoints; exempt list covers login and the cookie-less calendar feeds.
- **Sessions:** `HttpOnly` + `SameSite=Lax` + `Secure` (prod); 12h lifetime enforced by a `before_request` hook.
- **Audit:** sensitive supervisor actions append to `audit_log` (no UI by design).
- **Calendar feed auth:** the `/cal/<sigla>/<token>.ics` feed is **bearer-style** — the token is a per-employee secret. Treat it like a password; `/api/cal-link/rotate` rotates it. The single-shift `.ics` is session-gated and own-shift-only.

**Deliberately absent** (closed user group / intranet context): 2FA, OAuth/SSO, email/SMS confirmation, encryption at rest.

**Login redirect safety:** `?next=` is validated by an allow-list (`_is_safe_next`) that rejects `/login`, `/logout`, non-admin `/supervisor*`, and `/api/*`, so a logged-in employee following a supervisor link can't be bounced into a confusing loop.

## 13. Environment, running, and operations

**First run:**
```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
export AMORINO_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')"
export AMORINO_SUPERVISOR_PIN="<a strong PIN>"
python app.py
```
First run creates `amorino.db`, seeds `FUNCIONARIOS_SEED` + `TURNOS_SEED`, and auto-seeds headcount targets from observed peaks.

**Importing historical PDFs** (`import_history.py`, offline):
```bash
cp amorino.db amorino.db.backup-$(date +%Y%m%d)   # always back up first
python import_history.py --dry-run /path/*.pdf      # preview, writes nothing
python import_history.py /path/*.pdf                # idempotent import
python import_history.py --replace --reset-targets /path/*.pdf   # destructive rebuild
```
Flags: `--dry-run`, `--year N`, `--db PATH`, `--replace` (destructive: wipes a week's `Turno`s before reinserting — manual UI edits are lost), `--reset-targets` (recompute targets from observed peaks). Skips "Provas Práticas"/"Troca de Loja" rows and unknown siglas (reported, not silently created); auto-creates `SemanaConfig`; extracts the year from the filename (first 2000–2099 number, ignoring timestamp prefixes).

**Schema changes:** edit `models.py` **and** add an `ALTER TABLE` in the DB-init block of `app.py`. No Alembic.

## 14. Testing

- **Runner:** `cd <project> && python -m pytest tests/ -q`. The `-m` form puts the root on `sys.path` so `from app import ...` / `from models import ...` inside fixtures resolve.
- **Count:** **135 tests across 19 files** (at the time of writing).
- **Test deps:** `flask flask-sqlalchemy pytest holidays qrcode reportlab` (install with `--break-system-packages` in restricted environments).

**Fixtures (`tests/test_basics.py`):**
- `client` — a CSRF-aware test client. The login POST is CSRF-exempt, so the first POST works; later ones use the session token.
- `supervisor_client` — **the same `client` object**, pre-logged-in as `ADMIN` (PIN `1234`). **Critical:** do not request both `client` and `supervisor_client` in one test and try to hold two sessions — they're one client. To switch roles mid-test, just `client.post('/login', ...)` again as the other user.
- `employee_client`, `app` — also provided.
- Employee logins require a pre-provisioned valid PIN. The `employee_client` fixture explicitly provisions a fictional hash. Blank accounts require a supervisor-issued single-use invitation; see [Employee access](EMPLOYEE_ACCESS.md).

**Seed data in tests:** an active week and a past week exist. To test future-week behaviour, build a week with `helpers.time_helpers.week_from_monday` and insert a `SemanaConfig`.

**Testing-the-frontend caveat:** several features are client-side JS (relative-time label, calendar menu, panel-focus). Tests verify the *wiring* (data attributes, script presence, endpoint behaviour) rather than executing JS. When asserting a rendered class/element via substring, **strip `<style>`/`<script>` first** — otherwise a CSS rule like `.is-past {…}` or a JS `getElementById('x')` produces a false positive. (Both bit us; the fix is `re.sub(r'<style\b.*?</style>', '', html, flags=re.DOTALL)` and checking for `class="...the-class"`.)

**Test files (by area):**
`test_basics` (core), `test_login_bug`, `test_more_bugs`, `test_swap_conflict`, `test_calendar_reminders`, `test_assign_recommendations`, `test_central_candidatura`, `test_cross_week_swap`, `test_admin_central_readonly`, `test_nav_home_workflow`, `test_panel_assign_sync`, `test_panel_focus`, `test_headcount_unique_people`, `test_next_shift_relative`, `test_shift_calendar`, `test_minha_escala_shift_state`, `test_escala_improvements`, `test_homepage_widgets`, `test_availability_reminder`.

## 16. Critical gotchas and footguns

- **Dual template location (workspace only):** edits to `*.html` in the working-dir root don't take effect until copied into `templates/`. (Production usually has one location.)
- **`supervisor_client` IS `client`** — see §14. Holding two role sessions at once doesn't work.
- **Day label ≠ date.** `Turno.dia` is `'Seg 11'`; the real date is in `SemanaConfig.dias_json`. Always resolve through `dias_json`.
- **Week ordering by date, not id.** Use `semanas_chronological` / `semana_start_date`. Imported history can be out of insert order.
- **`scoring.py` touches the DB.** It imports `db`/`models` and queries inside the request context — don't call it outside one.
- **CSRF on `/api/*`.** Mutating API calls need the session CSRF token. The test `client` handles this; hand-rolled scripts/`curl` must send it (or hit a genuinely exempt endpoint).
- **Effective horários are computed, not stored.** `HORARIOS_BASE − HorarioSupressed + HorarioBloco`. Don't read `HORARIOS_BASE` directly when you need the live set.
- **Substring assertions match CSS/JS.** Strip `<style>`/`<script>` before checking for a rendered class/element (see §14).
- **No `ALTER TABLE` = silent breakage** on new columns. The init block in `app.py` is the migration mechanism.
- **The `(+1)` / `(+0,5)` markers** in horários are meaningful: `(+1)` crosses midnight (affects `shift_bounds`), `(+0,5)` is a paid half-hour. Non-time rows like `Provas Praticas` exist in `HORARIOS_BASE` too.

## 17. Known design decisions and open questions

**Conscious tradeoffs (not bugs):**
- **Calendar feed uses floating local time** (no VTIMEZONE). Correct for a single-timezone team (always Porto/Europe-Lisbon). Anchoring to a timezone would need DST rules for marginal benefit. Documented, intentional.
- **A person *can* hold two shifts in the same store on the same day** (split shift). Headcount counts them once (§11.1). If Amorino's policy is to forbid this, it should be a **separate** assignment-time validation — not assumed.
- **Routes stay in `app.py`** (no blueprints) and **no Alembic** — both revisit-later, not now.

**Open questions worth raising with the owner before building:**
- **Which week does `/disponibilidade` target?** Currently the *active* week. For a team collecting availability in advance, targeting the *next/drafting* week may be more intuitive — but changing it mid-cycle could surprise people. Ask first.
- **"Running late / can't make it today" flow.** The most common real-world daily event has no in-app answer yet. Needs design (notify the supervisor? flag the shift? copy a prefilled message?).
- **Calendar deep-link durability.** The Google "add by URL" / `render?cid=` forms occasionally shift; the copy-URL fallback covers it, but watch for breakage.
